Linux-Server & Node · Lektion 1

Die SSH-Haustür absichern

Ein frischer Hetzner-Server lässt sich als root mit Passwort einloggen — das ist die Tür, an der jeden Tag tausende Bots rütteln. In dieser Lektion schließt du sie ab: eigener Benutzer, Schlüssel statt Passwort, root gesperrt.

Ziel: Sicherer SSH-Zugang Dauer: ~20 Min Modus: Hands-on am echten Server
Was du danach kannst Einen neuen Server so absichern, dass Login nur noch mit deinem privaten Schlüssel und über deinen eigenen sudo-Benutzer möglich ist — root-Login und Passwort-Login sind tot. Das ist der erste und wichtigste Schritt jedes Server-Setups.

1 · Warum überhaupt?

Drei Begriffe, dann tippst du:

root ist der Admin-Account mit unbegrenzten Rechten. Der Name ist auf jedem Linux-System gleich — Angreifer müssen also nur noch das Passwort raten. Deshalb: nie direkt als root arbeiten oder einloggen.

sudo-Benutzer: ein normaler Account, der bei Bedarf mit sudo kurz Admin-Rechte „leiht“. Dein Alltags-Account. Angreifer kennen den Namen nicht.

SSH-Schlüsselpaar: ein privater Schlüssel (bleibt geheim auf deinem Windows-PC) und ein öffentlicher Schlüssel (liegt auf dem Server). Nur wer den passenden privaten Schlüssel hat, kommt rein. Ein Passwort kann man raten — einen 4096-Bit-Schlüssel praktisch nicht.

Reihenfolge des Abschließens — wichtig, damit du dich nicht selbst aussperrst:

1. Benutzer anlegen → 2. Schlüssel hinterlegen → 3. testen → 4. root + Passwort sperren

2 · Schlüssel erzeugen (auf deinem Windows-PC)

Falls du noch kein SSH-Schlüsselpaar hast: PowerShell öffnen und

ssh-keygen -t ed25519 -C "christopher@festival"

Enter bei allen Fragen (Standard-Pfad C:\Users\Du\.ssh\id_ed25519 reicht). Das .pub-File ist dein öffentlicher Schlüssel — den geben wir gleich dem Server. Das File ohne .pub ist privat und verlässt deinen PC nie.

ed25519 statt rsa Moderne Empfehlung ist ed25519 (kürzer, schneller, sehr sicher). Hast du schon einen id_rsa-Schlüssel im Einsatz, ist der völlig okay — dann diesen Schritt überspringen.

3 · Am Server: sudo-Benutzer anlegen

Logge dich (noch) als root ein — bei Hetzner meist mit dem Key, den du beim Erstellen hinterlegt hast, oder dem Initial-Passwort aus der Mail:

ssh root@DEINE_SERVER_IP

Neuen Benutzer anlegen (ersetze chris durch deinen Wunschnamen) und ihm sudo-Rechte geben:

# interaktiv: setzt ein Passwort + fragt ein paar (optionale) Infos
adduser chris

# in die sudo-Gruppe aufnehmen → darf künftig 'sudo' nutzen
usermod -aG sudo chris

-aG sudo: append (anhängen, nicht ersetzen!) zur Gruppe sudo. Das -a ist kritisch — ohne es würdest du den User aus allen anderen Gruppen werfen.

4 · Öffentlichen Schlüssel beim neuen User hinterlegen

Damit du dich künftig als chris per Schlüssel einloggen kannst, muss dein öffentlicher Schlüssel in dessen ~/.ssh/authorized_keys. Der bequemste Weg — von deinem Windows-PC aus (neues PowerShell-Fenster):

ssh-copy-id chris@DEINE_SERVER_IP

Geht ssh-copy-id unter Windows nicht, kopiere den Key manuell — am Server als chris (nicht root!):

# auf dem Server, eingeloggt als chris bzw. via 'su - chris'
mkdir -p ~/.ssh && chmod 700 ~/.ssh
nano ~/.ssh/authorized_keys   # Inhalt deiner id_ed25519.pub hier einfügen
chmod 600 ~/.ssh/authorized_keys

Rechte sind hier Pflicht, nicht Deko: SSH verweigert den Key-Login, wenn .ssh nicht 700 und authorized_keys nicht 600 ist (zu offene Rechte = SSH misstraut der Datei). Merke: 700 = nur der Besitzer darf alles, sonst niemand.

5 · TESTEN — bevor du irgendwas sperrst

⚠ Die wichtigste Regel

Schließe deine aktuelle root-Verbindung NICHT. Öffne ein zweites Terminal und teste den neuen Login. Erst wenn der funktioniert, machst du weiter. Sperrst du root/Passwort, ohne vorher den Key-Login getestet zu haben, und der Key klemmt — bist du komplett ausgesperrt.

# NEUES Fenster — altes root-Fenster offen lassen!
ssh chris@DEINE_SERVER_IP

Drin, ohne nach einem Passwort gefragt zu werden? ✅ Dann teste noch, ob sudo geht:

sudo whoami    # → muss "root" ausgeben (nach deiner Passwort-Eingabe)

6 · root- & Passwort-Login sperren

Jetzt — und erst jetzt — die Tür abschließen. Als chris mit sudo die SSH-Konfiguration bearbeiten:

sudo nano /etc/ssh/sshd_config

Diese drei Zeilen finden (Doppelpunkt-Such-Trick in nano: Strg+W) und so setzen — ggf. das führende # entfernen:

PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes

PermitRootLogin no → root kann sich gar nicht mehr per SSH einloggen.
PasswordAuthentication no → Login geht nur noch per Schlüssel, kein Passwort-Raten mehr möglich.
PubkeyAuthentication yes → Schlüssel-Login bleibt erlaubt (Standard, zur Sicherheit explizit).

Speichern (Strg+O, Enter, Strg+X), dann SSH neu laden:

sudo systemctl restart ssh
⚠ Letzter Test vor dem Schließen Wieder im noch offenen Fenster: öffne ein drittes Terminal, logge dich erneut als chris ein. Funktioniert? Erst dann darfst du die alte root-Session schließen. Geht's schief, kannst du im offenen Fenster den Fehler beheben.
Notausgang Hetzner Sperrst du dich trotzdem aus: Hetzner Cloud bietet eine Web-Konsole (im Projekt-Dashboard, „Console“) — wie ein Monitor direkt am Server, kommt ohne SSH rein. Dort kannst du die sshd_config wieder reparieren. Gut zu wissen, dass es das gibt.

Checkliste — am echten Server abhaken

  • SSH-Schlüsselpaar auf dem Windows-PC vorhanden (ed25519 oder rsa)
  • sudo-Benutzer angelegt (adduser + usermod -aG sudo)
  • Öffentlicher Schlüssel beim neuen User hinterlegt (Rechte 700/600)
  • Login als neuer User per Schlüssel getestet — ohne root-Fenster zu schließen
  • sudo whoami gibt root
  • PermitRootLogin no + PasswordAuthentication no gesetzt
  • sudo systemctl restart ssh ausgeführt
  • Neuer Login NACH dem Restart erneut getestet ✅

Als Nächstes
