Effect vs. tRPC verschiedene Achsen

Kurze Antwort: Es ist meist kein „entweder/oder“. tRPC und Effect lösen Probleme auf zwei verschiedenen Achsen — und lassen sich kombinieren.

⏱ ~9 Min 🎯 Mission: lohnt es sich? 🧩 Du kennst: tRPC (Monorepo), Effect<A,E,R> aus Lektion 1

Die Verwechslung, die du gerade hast

Du kennst tRPC als „typsichere API von Client zu Server“. Effect klingt auch nach „typsicher + Fehler im Typ“. Naheliegend, sie als Konkurrenten zu sehen. Sind sie aber meistens nicht — sie sitzen auf unterschiedlichen Achsen:

Achse 1 · Transport / Vertrag (Client ↔ Server)
tRPC @effect/rpc REST / OpenAPI GraphQL

„Wie reden Client und Server typsicher miteinander?“ — Router, Procedures, Serialisierung, ein Client-Typ aus dem Server abgeleitet.

Achse 2 · Logik innerhalb einer Funktion (Fehler, Deps, Komposition)
Effect plain async/await + try/catch neverthrow (Result)

„Wie schreibe ich die Business-Logik im Handler?“ — typisierte Fehler (Slot E), Dependencies (Slot R), Retry, Komposition.

Mentales Modell

tRPC ist das Rohr zwischen Client und Server. Effect ist, was im Rohr fließt — wie du die Logik im Handler baust. „Was fließt“ ist unabhängig vom Rohr. Deshalb: du kannst Effect in deinen tRPC-Procedures benutzen, ohne tRPC aufzugeben.

Wo es sich doch direkt vergleicht: @effect/rpc

Es gibt einen echten 1:1-Konkurrenten zu tRPC im Effect-Lager: @effect/rpc. Das ist Achse 1 aus dem Effect-Ökosystem — die Alternative, wenn du den Transport auch in Effect-Sprache (mit Schema end-to-end) haben willst. Manche ersetzen tRPC komplett dadurch; meist erst dann sinnvoll, wenn der Rest der App schon Effect ist.

Erfahrungsbericht (tRPC → @effect/rpc, Next.js): titouancreach, DEV

Der übliche Weg: kombinieren

tRPC bleibt das Rohr. Die Logik im Handler schreibst du als Effect (lazy Beschreibung, Lektion 1) und führst sie genau an der Grenze aus — im Procedure. Typisierte Fehler mappst du dort auf TRPCError.

// 1) Logik = Effect. Fehler stehen im Typ (Slot E), keine throws.
const getUser = (id: string): Effect.Effect<User, UserNotFound> => /* … */

// 2) Ein Helfer, der den Effect an der tRPC-Grenze ausführt
//    und erwartete Fehler in TRPCError übersetzt.
async function runAtBoundary<A, E>(effect: Effect.Effect<A, E>) {
  const exit = await Effect.runPromiseExit(effect)
  return Exit.match(exit, {
    onSuccess: (a) => a,
    onFailure: (cause) => { throw toTRPCError(cause) }  // E → TRPCError
  })
}

// 3) Im Procedure: Effect bauen, an der Grenze ausführen.
const userById = publicProcedure
  .input(z.object({ id: z.string() }))
  .query(({ input }) => runAtBoundary(getUser(input.id)))

Das ist exakt das Muster aus Lektion 1 in der Praxis: Effect = Beschreibung, und runPromiseExit ist das „Kochen“ — und zwar am Rand (im Procedure), nicht mitten in der Logik. tRPC will ein Promise oder einen throw; der Helfer übersetzt dorthin.

Muster (Exit-Match → TRPCError, Helfer via Middleware/Context injizieren): macwright: Effect notes — tRPC · Effect-Community: ManagedRuntime + Effect.fn für Stacktraces

Profi-Variante

Statt blankem runPromise nutzt man eine ManagedRuntime: dort steckst du einmal deine Services/Layer rein (der R-Slot aus Lektion 1) und rufst MyRuntime.runPromise(effect). So füllst du Dependencies einmal und nicht pro Request neu. (Kommt als eigene Lektion — hier nur als Ausblick.)

Die eine echte Reibung: Schema als tRPC-Validator

Wenn du Effects Schema als tRPC-input-Validator verwenden willst, knirscht es. Grund: tRPC nimmt an, dass Eingabe-Typ = Ausgabe-Typ des Validators ist. Effects Schema aber dekodiert oft (z. B. string → Date) → Eingabe ≠ Ausgabe. Ergebnis: manuelles En-/Decode auf beiden Seiten, fehleranfällig.

Praktische Konsequenz

Pragmatisch: für den tRPC-input bei Zod bleiben (oder simplen Validatoren), und Effect innen für Logik/Fehler/Deps nutzen. Willst du Schema wirklich end-to-end → das ist genau der Punkt, an dem @effect/rpc attraktiv wird.

Reibungspunkt belegt in beiden Erfahrungsberichten: macwright · titouancreach.

Sofortiges Feedback — anklicken, kein Submit.

1. Auf welcher „Achse“ konkurriert Effect direkt mit tRPC?

✔ Genau. @effect/rpc ist der 1:1-Gegenspieler zu tRPC (Transport). Das Kern-Effect dagegen lebt im Handler (Logik) und ist mit tRPC kombinierbar.
Zwei Achsen: Transport (tRPC ↔ @effect/rpc) und Logik (Effect im Handler). Kern-Effect ersetzt tRPC nicht — es füllt das Rohr.

2. Du benutzt Effect in einer tRPC-Procedure. Wo rufst du runPromiseExit auf?

✔ Richtig. Logik bleibt lazy Effect (Beschreibung); ausgeführt wird am Rand, genau dort wo tRPC ein Ergebnis braucht. Dort mappst du E → TRPCError.
Erinnere Lektion 1: Effects sind lazy. Du hältst die Logik als Beschreibung und führst sie einmal an der Grenze aus (Procedure-Handler), nicht überall verstreut.

3. Warum knirscht Effects Schema als tRPC-input-Validator?

✔ Sitzt. Genau dieser Input-/Output-Mismatch erzwingt manuelles En-/Decode. Pragmatisch: Zod für input, Effect innen — oder gleich @effect/rpc.
Es ist kein Performance- oder GraphQL-Thema: tRPC erwartet Validator-Eingabe = -Ausgabe, Schema transformiert aber (z. B. string→Date).

4. Dein Team nutzt tRPC und will Effects Nutzen schrittweise testen. Bester erster Schritt?

✔ Genau das ist der Charme des Kombi-Wegs: kleiner Radius, kein Transport-Umbau, sofort der E/R-Nutzen — und jederzeit umkehrbar.
Du musst weder alles migrieren noch erst Theorie pauken. Der risikoarme Einstieg ist Effect in einer Procedure, an der Grenze ausgeführt.

Dein Win

Du kannst jetzt sagen: tRPC und Effect sind nicht dasselbe und meist kein „entweder/oder“ — tRPC ist das Rohr (Transport), Effect ist, was im Rohr fließt (Logik). Direkter Konkurrent zu tRPC ist nur @effect/rpc. Und du kennst den konkreten Kombi-Weg (Effect im Handler → runPromiseExit an der Grenze → TRPCError) plus die eine Reibung (Schema als Validator). Genug, um für dein Monorepo eine begründete „lohnt sich / lohnt sich nicht“-These zu bilden.
